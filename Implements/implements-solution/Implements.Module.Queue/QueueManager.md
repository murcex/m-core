# QueueManager — Summary

-- Purpose
  - `QueueManager<T>` batches `T` items and invokes a provided `Action<List<T>>` when either the queue reaches a configured `limit` or a configured `duration` (milliseconds) elapses.

-- Public API
  - `QueueManager<T>(int limit, int duration, Action<List<T>> action, Action<string>? logger = null)`
  - `bool Enqueue(T item)`
  - `bool Shutdown()`
  - `bool IsActive()`

- Key behavior
  - Uses `ConcurrentQueue<T>` to store items.
  - On first enqueue when inactive, starts a long-running timer task (`AsyncTrigger`) that waits `_duration` then processes.
  - If active and `_queue.Count >= _limit`, cancels the token to force immediate processing (`Trigger`).
  - `ExecuteTrigger` drains the queue into a `List<T>` and calls the provided `_action`.
  - Logging via a pluggable `Action<string>`; short instance ids generated by `GetInstanceId()`.

- Notable issues / risks
  - Shared state fields (`_active`, `_processing`, `_shutdown`, `_token`) are accessed from multiple threads without atomic operations or locks — race conditions possible.
  - Uses `_queue.Any()` + `TryDequeue` loop instead of repeated `TryDequeue` until false.
  - `CancellationTokenSource` instances are recreated but not disposed.
  - Tasks started with `Task.Factory.StartNew(...).ConfigureAwait(false)` are not awaited; exceptions may be lost.
  - `AsyncTrigger` uses `Task.Delay(...).ContinueWith(...)` which can be simplified and may behave unexpectedly on cancellation.
  - `using System.Transactions;` is unused.
  - Non-generic queue (`object`) reduces type safety.

- Suggested improvements
  - Use `Interlocked` or `lock` to guard state transitions.
  - Drain queue with `while (_queue.TryDequeue(out var item)) { list.Add(item); }`.
  - Dispose replaced `CancellationTokenSource` instances.
  - Use `Task.Run` / `await` with proper exception handling for trigger tasks.
  - Simplify `AsyncTrigger` to `await Task.Delay(_duration, token)` and handle `TaskCanceledException`.
  - Consider `QueueManager<T>` generic and remove unused `using`.

# QueueManager — Usage Example

```csharp
using Implements.Module.Queue;

var queueManager = new QueueManager<string>(100, 5000, ProcessQueue);

for (int i = 0; i < 1000; i++)
{
    queueManager.Enqueue($"Message {i}");
}

queueManager.Shutdown();

void ProcessQueue(List<string> messages)
{
    foreach (var message in messages)
    {
        Console.WriteLine(message);
    }
}
```

# QueueManager — Known Issues

- **Thread safety**: The current implementation accesses shared state fields from multiple threads without appropriate synchronization mechanisms like locks or Interlocked operations. This can lead to race conditions and unpredictable behavior in a multi-threaded environment.
- **CancellationToken disposal**: `CancellationTokenSource` instances are recreated on each trigger but are never disposed, potentially leading to memory leaks.
- **Unobserved task exceptions**: Tasks that are started with `Task.Factory.StartNew(...).ConfigureAwait(false)` are not awaited, which means any exceptions they throw will be unobserved and can cause application crashes or other unintended behaviors.
- **AsyncTrigger implementation**: The usage of `Task.Delay(...).ContinueWith(...)` in `AsyncTrigger` is not only unnecessary complicated but might also result in unexpected behavior when the task is canceled. Simplifying this to a direct `await Task.Delay(..., token)` approach would be more in line with modern async/await patterns and would automatically handle the cancellation case.
- **Unused namespaces**: The `using System.Transactions;` directive is unnecessary and should be removed to clean up the code.
- **Non-generic queue**: The usage of a non-generic queue (`object`) reduces type safety, making the code prone to runtime errors that could be caught at compile time if generics were used.

Improvements addressing these issues would enhance the robustness, performance, and maintainability of the `QueueManager` implementation.

# QueueManager — Test Cases

The following test cases should be implemented (unit and integration style) to adequately cover `QueueManager` behavior.

1. Enqueue triggers processing on limit
   - Arrange: new `QueueManager(limit: 5, duration: 10000, action: capture)`
   - Act: call `Enqueue` 5 times quickly
   - Assert: `capture` is invoked once with 5 items; queue is empty after processing.

2. Enqueue triggers processing on duration
   - Arrange: `QueueManager(limit: 100, duration: 100, action: capture)`
   - Act: call `Enqueue` fewer than limit, wait > duration
   - Assert: `capture` is invoked once with the enqueued items.

3. Multiple batches over time
   - Arrange: `limit: 3, duration: 50` and an `action` that records batches
   - Act: enqueue 7 items with small delays to create 3 batches (3, 3, 1)
   - Assert: `action` called three times with expected batch sizes and total items processed == 7.

4. Shutdown prevents further enqueues and cancels pending trigger
   - Arrange: start manager and enqueue some items
   - Act: call `Shutdown()` then attempt more `Enqueue`
   - Assert: `Shutdown()` returns true; subsequent `Enqueue` returns false; pending trigger is cancelled and final `action` may run once for items before shutdown.

5. IsActive reflects trigger lifecycle
   - Arrange: new manager with short duration
   - Act/Assert: after first `Enqueue` `IsActive()` is true until the batch is processed; after processing `IsActive()` is false.

6. Action exceptions are caught and logged
   - Arrange: set `action` to throw; supply a logger capturing messages
   - Act: enqueue enough items to trigger processing
   - Assert: exception does not propagate to caller; logger received entries indicating exception and exception text.

7. Concurrent enqueues do not cause concurrent processing
   - Arrange: large number of threads/tasks concurrently calling `Enqueue`
   - Act: verify that `action` never runs concurrently (use a synchronization flag inside `action` to detect re-entry)
   - Assert: no concurrent execution detected; all items eventually processed.

8. Replacing CancellationTokenSource disposed (resource management)
   - This is more of an integration/resource test: exercise multiple triggers and ensure disposal is called (if implementation is changed to track disposals) or at least ensure no unbounded resource growth over time.

9. Unobserved task exceptions are prevented
   - Arrange: make `action` throw and ensure trigger tasks are awaited/observed in the future implementation
   - Act: trigger processing via limit or duration
   - Assert: no unobserved task exceptions escape (use TaskScheduler.UnobservedTaskException hook in integration tests if needed).

10. Queue drains completely during ExecuteTrigger
    - Arrange: enqueue items while a trigger is executing (race)
    - Act: ensure items enqueued after the processor starts are either included in the same batch (depending on timing) or processed by a subsequent trigger, but never lost.

11. Large-volume throughput and stability
    - Integration test that enqueues tens of thousands of items over time to validate stability, memory usage, and correct batching under load.

12. Logging behavior
    - Provide a logger implementation that captures messages
    - Assert that key lifecycle events are logged (queue_async_triggered, queue_limit_triggered, processor_action_count, action_status completion/exception).

Notes on timing-sensitive tests
- Use deterministic timing where possible by injecting smaller durations and using synchronization primitives (TaskCompletionSource) inside the action to control test flow.
- For concurrency tests, use repeated runs and stress schedules to reduce flakiness. Consider making some tests integration/long-running rather than unit tests.
